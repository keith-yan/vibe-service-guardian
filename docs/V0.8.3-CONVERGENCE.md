# Vibe Service Guardian 0.8.3 收敛边界

0.8.3 不是功能扩张版本。它把 0.8.1–0.8.2 已有的“评估—显式操作—验证—恢复”闭环，从模拟单元测试推进到可重复、隔离、可审计的本机证据，并补齐历史库升级与依赖供应链边界。

## 一、主动动作只验证测试夹具

### 1. 关停、端口与自动拉起

- `tests/fixtures/vsg_fixture_service.py` 只监听随机分配的 `127.0.0.1` 端口，并写入测试临时目录中的 PID 状态。
- 普通场景创建“监听父进程 + 空闲子进程”，真实调用 `terminate_process_tree()`，再验证父子 PID 消失、端口关闭、无遗留进程。
- 自动拉起场景由独立看门狗重建测试服务，验证替代 PID 和重新绑定端口能在有限观察窗内被识别为 `relaunched`。
- 验证器的 `second_stop_attempted` 必须保持 `false`；新进程只被报告，不会被 VSG 自动再次结束。
- 清理逻辑只接收夹具自己记录的 PID/创建时间。测试不枚举或按名称结束其他服务。

### 2. 假模型运行时与固定矩阵

- `tests/fixtures/fake_model_runtime.py` 是回环 HTTP 服务，不加载权重、不访问网络、不使用 GPU。
- 固定矩阵真实执行单请求 5 次、双并发 10 次、四并发 20 次，共 35 次请求；不会自动扩展计划。
- 同一夹具覆盖 Ollama NDJSON 与 OpenAI 兼容 SSE，另覆盖协作式中止、HTTP 认证拒绝、OOM 错误脱敏。
- 结果只持久化 token 数、TTFT、吞吐、错误类别和资源采样；测试使用唯一响应文本反查 SQLite，证明生成正文未入库。

这些测试证明的是 VSG 控制逻辑和协议边界，不代表任何真实模型、真实 GPU 或第三方推理引擎已经完成性能验收。

## 二、SQLite schema version 4

历史数据库初始化顺序固定为：

1. 对现有数据库执行 `PRAGMA quick_check`；
2. 若数据库版本高于当前程序支持版本，拒绝降级打开，不做迁移；
3. 若旧库需要升级，先用 SQLite backup API 创建同目录一致性备份；
4. 在 `BEGIN IMMEDIATE` 单事务中逐版本迁移并更新 `PRAGMA user_version`；
5. 任一步骤失败即回滚，备份保留；
6. 若文件被 SQLite 明确认定为损坏，关闭连接后将主文件及已存在的 WAL/SHM 精确改名隔离，再创建新库；损坏原件不会删除。

Web 快照只返回 schema 版本、完整性状态和备份/隔离文件名，不返回数据目录绝对路径。备份和隔离库仍可能包含本机历史，因此继承本地私有文件权限，不应上传到 Issue 或公开仓库。

version 4 新增 `impact_feedback`：每个服务指纹最多一条可更新的人工结果，只保存结果、判断时风险等级/分数、来源分组和时间。升级 version 3 数据库时仍先生成一致性备份；该记录跟随历史保留策略，并可通过 `CLEAR HISTORY` 单独清除。

## 三、wheel 哈希锁

`requirements-lock/` 包含 20 份锁文件：

- Windows x64、macOS arm64/x86_64、Linux x86_64/aarch64；
- Python 3.10、3.11、3.12；
- 各平台运行锁和构建锁；
- 统一 pip 引导锁；
- Linux/Python 3.12 CI 审计工具完整依赖锁。

锁生成器只允许公开 PyPI HTTPS，清除 `PIP_*` 配置，强制 wheel 并记录每个归档 SHA-256。安装入口使用 `--require-hashes` 与 `--only-binary=:all:`；显式列全依赖的运行/构建锁再使用 `--no-deps`，避免安装时重新解析隐式依赖。

`python scripts/Requirement-Locks.py --verify` 是离线门禁，只验证签入锁是否完整、源依赖是否变化和文件摘要是否匹配。只有维护者明确更新依赖时才应执行联网的 `--generate`，并重新完成漏洞审计与三平台 CI。

## 四、Docker/WSL 归属契约

Docker 和 WSL 服务都输出 `attribution_contract.version = 1.0`：

- Docker 的身份主键是 container ID；`docker inspect` 的 `State.Pid` 只标记为 engine-reported PID，`host_pid` 固定为未知，不假设它是 Windows/macOS 宿主 PID。
- Docker 端口只表示观察到的 published host port；Compose 项目、服务和工作目录只来自长度受限、无控制字符、格式合法的标准标签。
- WSL `process.pid` 表示发行版内部 Linux PID；`windows_host_pid` 固定为未知。
- WSL `ss/netstat` 端口表示 guest listener；是否由 Windows localhost forwarding 暴露明确标记为 `not_verified`。
- Docker Engine/Compose 与 WSL distribution 是生命周期管理器；VSG 不通过宿主机 STOP 链路管理这些对象。

## 五、CI 门禁

`.github/workflows/ci.yml` 定义：

- Windows、macOS、Linux × Python 3.10/3.12 的六组合测试；
- 锁文件离线一致性、编译、公开目录审计；
- Ruff、Bandit 中/高风险和四组依赖漏洞审计；
- Windows、macOS、Linux 的 Python 3.12 原生 PyInstaller 构建与回环启动验收。

本地只能验证 YAML、脚本、锁安装和当前 Windows 构建路径。工作流没有在 GitHub 托管 runner 上执行之前，macOS/Linux 原生结果和 GitHub required-check 状态仍属于未验证项。

## 六、本机成效证据

- 服务详情允许记录“确属遗留 / 不是遗留 / 暂不确定”；同一服务指纹使用 upsert，不因重复点击增加样本数。
- 顶部弹窗只展示当前聚合与保留期历史聚合；导出必须输入 `EXPORT REPORT`，文件包含规范化报告的 SHA-256。
- 报告字段采用白名单构造，不序列化服务对象；不含 PID、路径、IP、命令、会话 ID、日志或模型响应。
- 报告固定声明它是单机、自报、受保留期限制的证据，并把外部采用验证标记为 false；不能用来替代独立案例、公开下载或社区维护记录。
- 运行时无自动遥测、无上传目标、无后台导出。

## 七、明确不做

0.8.3 不新增远程控制、多用户账户、自动停止、自动基准、自动 OOM 探测、凭据读取、模型下载、驱动/防火墙修改、Docker/WSL 控制或云端遥测。真实服务的 `STOP` 与 `BENCHMARK` 仍必须由用户针对具体目标逐次确认。
